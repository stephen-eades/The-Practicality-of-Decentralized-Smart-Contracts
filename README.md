## Problem Statement
Blockchain technology has shown that the removal of trust in a system is possible, and many are wondering how this new technology will fit into a world where trust seems more important that ever. Smart contracts and decentralized applications on the Ethereum Blockchain have been a major point of focus in the newfound industry, and developers have begun to explore what this technology is capable of. However, there has yet to be major usage of decentralized applications by the general population. One concern is that the current costs associated with making transactions on a blockchain can be exorbantly high, as scaling and protocol solutions are still being implemented. These high costs likely drive potential users away from decentralized systems. Another issue is that a majority of current dapps are for financial services that a regular person wouldn't often use. Decentralized exchanges (DEXs) and decentralized lending and money markets, also known as Decentralized Finance (Defi), dominate the current dapp ecosystem. Most users of these dapps are wealthy indivudals and institutional investors looking for liquidity, arbitrage, and investment opportunities. 

Blockchain technology could help remove the middleman, and trust, from many situations where it would benefit the end users. Imagine a smart contract that automatically calculates and allocates your retirement funds for you based on your risk assessment, market conditions, and preferences, ultimately removing the need for a financial advisor. A decentralized version of many current platforms (Facebook, Uber, etc.) would remove the need for centralized servers and storing user data, which means companies would have an easier time with regulations like GDPR. Elections could be held entirely on a blockchain, allowing any user to check and validate any other vote that occurred, ensuring a election process that can't be tampered with or manipulated. These ideas all sound wonderful on paper, but how effective and practical they are for the user is yet to be determined. With the afforementioned concerns stated above, one might assume that these kind of decentralized applications and products are still years out from being ready for everyday usage by the general population. 

The dapp that I developed provides the user the ability to create and deploy their own smart contract event. The user simply inputs the event details, and the deployment process implements their details into the event logic. Similiar studies tended to evaluate a specific transaction and how it varied with time and the price of Ether, while my application will additionally explore and compare multiple transaction types (transfering Ether, deploying contracts, writing to contract storage, etc.) and how the user's input for the creation of each contract impacts the cost. I also believe the ability to let the user customize their own smart contract could be a way to help grow the adoption of decentralized applications for day-to-day usage. I hope my project can give future users, researchers, and developers awareness on the benefits and downsides of using and building a decentralized application. If successful, blockchain technology and decentralization could revolutionize how we exchange value and automate processes that require trust.

This dapp structure begins with the frontend, which handles receiving the user input and sending to the backend i.e. smart contract. This occurs through the web.js api, with the help of Drizzle which uses React's context and state management to keep the frontend synced with the smart contracts data that it connects to. On the receiving end of the frontend's requests is the main `EventManager.sol` contract. This can be thought of as the parent that manages the child contracts, and exposes getter functions so the frontend can access data on any existing contracts that have been deployed. This contract can create new contracts by sending a request to the `EventCreator.sol` which has the sole job of creating and deploying event contracts for the EventManager contract to manage. The three smart contract event types are `PollEvent.sol`, `EscrowEvent.sol`, and `LotteryEvent.sol`. They each utilize a constructor that handles the initial configuration of the events logic. For exampe, candidate names for polls, involved parties for escrows, and ticket price for lotteries are all mapped to the contract's storage during this constructor process. At this point, the event contract has been configured and contains all the functions and logic needed to process that type of event. Below we will look at the struct in each contract event to better understand their makeup:

```

/**                       /**                            /**      
Poll Candidate            Escrow Member                  Lottery Ticket       
*/                        */                             */    
struct Candidate {        struct Member {                struct Ticket {                                                               
   uint id;                  uint id;                       uint id;
   string name;              address memberAddress;         address owner;                   
   uint voteCount;           uint currentDeposit;           uint number;
}                            uint requiredDeposit;          string status;
                           }                                bool winner;
                                                         } 
```

The `PollEvent.sol` contract maps each Candidate struct to their ID, and includes their name and total votes the candidates received. Poll events additionally map each address that votes in the poll so we can prevent any user from voting twice. Other functions for adding candidates, casting a vote, and getting data about the Poll are exposed so the frontend can grab what it needs and provide data to update the smart contract state. `EscrowEvent.sol` takes a similiar approach in how it stores each member involed in the escrow, mapping it to their ID and storing their address. Additionally the required amount the member must deposit, and the current amount they actually have deposited are stored and updated as the members make their deposits. The stored members address is used to validate that the frontend user attempting to deposit matches the address that was assigned to participate in the escrow. Finally, the `LotteryEvent.sol` contract follows the same pattern, mapping each created Ticket to its ID. A unique number is generated during construction and is assigned to each ticket, along with the status of if the ticket has been purchased or not, and if the ticket is the winner. This pattern of structing a data model, mapping it to storage, and updating its values through setters encompasses the basic pattern of a decentralized application.  

When discussing the logic used in a decentralized application, and in particular in smart contracts, we have to remember that each time we write to the blockchain, it costs the user money. Each additional loop we must make, each additional variable that needs incremented, and any unnecessary code all falls back onto the user in additional transaction feed. While developing this dapp, I had to constantly keep this in mind as the transaction data I would be gathering for my analysis could be heavily impacted by the computation my smart contracts required. 

Other challenges arose during development, and they stem from the fact that Solidity is a deterministic language. This is because each node needs to be able to get the same exact results with the given input for a method. Without this, it would not be possible to keep consensus within the network. Determinisitic languages means generating a random number isn't possible without work arounds or 3rd party solutions. I ended up using the `keccak256` hash function and the current block timestamp to create a pseudorandom number. The blockchain also has no concept of time, so I had to resort to using `uint` data types to store the block timestamp, which is the same as the Unix timestamp. Because of the difficulty of evaluting passing time, the expiration date for each contract event type may be off by up to a couple hours. The final hurdle is the fact that anything on a smart contract can be read by the user. This meant that the lottery contract which contains the information regarding the winning ticket could be viewed by a user if they really wanted to find it. The solution to this would require a third-party oracle, which is a service that can provide external information to a smart contract.

### Experience with Event Contracts:
Each event contract had unique logic needed to ensure they functioned properly. Additional layers of complexity could be added to make each event more customizable, however in keeping with my goal of simplicity, I included only what was necessary to make each event contract function in it's most basic form. As discussed above, too much complexity and you risk raising the amount of gas the user must pay for transactions. Once deployed, each event can be found on the Browse page, or by searching for the event's contract address on the Search page. Each contract type and their details are described below:

* Poll Event Contract: Poll events allow a user to create there own voting process contained in a single contract deployment. The authoring user names the poll, sets an expiration date for the poll, and can add candidates that can be voted for. When viewing a deployed poll, any other user can spend ethereum to cast their single vote. After the contract expires, no more votes can be cast and the winner can be viewed. This event type was most simple, and likely will require the least amount of gas to deploy and interact with. 

* Escrow Event Contract: Escrow events allow a user to create a escrow process contained in a single contract deployment. The authoring user names the escrow, sets the expiration, sets the required amount that each member of the escrow must deposit, and can add the address of any other user that they want to be part of the escrow. When viewing a deployed escrow, only the users who have designated addresses assigned to the escrow may interact with it. The designated users can deposit the required amount of Ether which the contract will lock up until the contract expires. At that point, the users will then be able to withdraw their deposited amount back to their own address from the contract. This event type was slighly more complex than the poll event, thus will probably use more gas as well.  

* Lottery Event Contract: Lottery events allow a user to create a lottery process contained in a single contract deployment. The authoring user names the lottery, sets the expiration, sets the total number of tickets to be generated in the lottery, and sets the cost to purchase a ticket. When viewing a deployed lottery, any other user can purchase as many tickets as they'd like. When purchasing a ticket the user will have their address assigned to it, and will transfer the cost of the ticket to the smart contract to lock up until expiration. Once expired, users can view the lottery and attempt to claim there ticket to see if it was the winner. Claiming a winning ticket will result in the contract sending the entire balance it received from the purchased tickets to the that users address. Certainly more complex than the poll and escrow event, this will likely use the most gas to deploy and interact with. 

## Evaluation Metric
The Ethereum network uses it's native token, Ether, as gas. This gas is the fee that is spent during each transaction, and currently goes to the miners of the network as a reward for validating blocks and keeping the chain in consensus. Gas is usually expressed in small fractions of Ether, and is commonly referred to by the unit "gwei". The price of Ether can be volatile, meaning gas prices are always in flux. High network congestion also impacts gas prices, as the miners must price the gas in accordance with supply and demand on the network. To evaluate the transactions of this dapp, we will be expressing costs in terms of gwei and the United States Dollar (USD). We will evaluating how transactions costs differ amongst transaction type, how costs differ for the same transaction over a period of time, and how the price of Ether impacts transaction costs over a period of time.
